# services/api/

## Purpose
Centralized API client layer: one file per backend domain, each exporting a factory `(apiCaller) => ({ methodName(config) {...} })` that wraps raw HTTP calls into named functions. `index.js` aggregates every domain factory into a single `$api` object (registered via `nuxtApp.provide('api', ...)` in [`plugins/api.js`](../../plugins/CLAUDE.md)), so app code calls `$api.<domain>.<method>(config)` instead of hitting `$fetch` directly.

## Public surface — the shared request contract
Every domain factory receives a shared `apiCaller` built in [`plugins/api.js`](../../plugins/CLAUDE.md), exposing `get/post/put/patch/delete(url, config)`. Every integration task depends on this contract:
- `config.data` → request body, `config.params` → query string, `config.instance` → which `$fetch` instance to use (`'default'` or `'cms'`; defaults to `'default'`).
- Two `$fetch.create` instances: `default` (baseURL = `runtimeConfig.public.BACKEND_URL`, injects `Authorization: Bearer <cachedToken>` client-side only) and `cms` (baseURL = `runtimeConfig.public.CMS_URL`, adds `Strapi-Response-Format: v4`, server-side only).
- `onResponse` wraps **successful** bodies as `response._data = { data: response._data }` — callers must read `response.data.data` (or `.data.data.content` for paginated lists).
- `onResponseError` instead does `response.data = response._data; delete response._data` — only one level of wrapping. On failure, `error.response.data` holds the raw backend error body directly, `error.response.status` holds the HTTP status. **This asymmetry is easy to get wrong** — a naive `error.response.data.data` is `undefined`.
- `apiCaller.get` memoizes in-flight promises in a module-level `Map` keyed by `url + JSON.stringify(params)` (not including `instance`), auto-evicting on settle. Only `get` de-dupes; `post/put/patch/delete` never cache.
- **No global 401/403 handling** — each caller inspects `error?.response?.status` itself (see [`plugins/auth.client.js`](../../plugins/CLAUDE.md) and `utils/auth.js::logoutAndResetAuthentication`).

## Data flow and dependencies
- Consumed as `$api.<domain>` (`nuxtApp.$api`) or `app.$api.<domain>` (via `useNuxtApp()`).
- **Actual current wiring**: `auth.js` (login/register/OTP, `pages/login.vue`, `plugins/auth.client.js`, `utils/auth.js`), `panel/address.js` (`pages/panel/address.vue`), `products.js::fetchProductsList` (`pages/medications/index.vue`), and now `orders.js` (`byPerson`/`searchOrders`/`searchOrdersByStatus`) + `catalog.js::getCatalogsByType` — both called from `components/panel/orders/{CustomerOrders,OrdersManagement}.vue` (see [`components/panel/CLAUDE.md`](../../components/panel/CLAUDE.md)). `orders.js`'s other methods (`listOrders`, `getOrder`, `createOrder`, `deleteOrder`, `byUser`, `byStatus`, `byDate`, the order-item/invoice/purchase-order CRUD) remain unverified-but-plausible against BACK source — verified ones noted inline above.
- The remaining ~16 domain files (`goods`, `payments`, `inventory`, `analytics`, `communication`, `user`, `organization`, `location`, `search`, `medical`, `attachment`, `settings`, `audit`, `dynamic`, `sms`, `blog`) plus the unverified parts of `catalog.js`/`orders.js` are scaffolded per the pre-existing `BACKEND_INTEGRATION.md`/`API_ENDPOINTS_SUMMARY.md` docs for future admin-panel/store work and have **no current store/page callers** — treat their shapes as provisional/unverified against the live backend until confirmed against BACK source.
- No shared error-normalization helper exists — each caller re-derives status/message ad hoc (e.g. `plugins/auth.client.js` checks `[401,403]`; `login.vue` just toasts a generic error; `utils/auth.js` swallows errors silently).

## Gotchas
- **Double address domains**: `location.js` (`$api.location`, POST-based `api/addresses/*`) and `panel/address.js` (`$api.address`, mixed GET/POST `/api/addresses/*`) both model "addresses" with different endpoints/shapes and separate namespaces.
- **Double blog domains**: `blog.js` (`$api.blog.getBlogPosts`, CMS/Strapi GET) vs. `communication.js`'s blog CRUD (`$api.communication`, backend POST) — same subject, different backends, no naming hint which to use.
- **`products.js` vs `goods.js`**: `products.js` is explicitly commented "Legacy alias" wrapping the same `api/goods/list` endpoint `goods.js::listGoods` covers, but don't assume identical response shape.
- **GET caching is barely exercised**: almost every domain implements list/get as `apiCaller.post(...)` even for pure reads, so only `auth.fetchUser`, `attachment.downloadAttachment`, `blog.getBlogPosts`, `panel/address.getState` actually use the de-duped `get` path.
- **`blog.js::getBlogPosts`** spreads `...config` then unconditionally overwrites `params: { populate: '*' }` — silently discards any `params` the caller passed in.
- **Inconsistent leading slash**: most domain files use bare paths (`'api/goods/list'`); `blog.js`/`panel/address.js` use leading-slash paths. Harmless with `$fetch` baseURL joining, but inconsistent style.
- **`auth.js::submitOtp` bug**: calls `this.login(config)`/`this.register(config)` without `return`/`await` — the result is dropped; callers awaiting `submitOtp` get `undefined`. Fix this when touching the OTP flow.
- **CRUD asymmetry across domains**: some have full CRUD (goods, orders, inventory, catalog, user, medical); others are read/update-only with no delete (`settings.js`, `search.js`). Naming also diverges (`getUser`/`listUsers` hit `api/persons/*`).
- **No shared validation/typing** — `config` objects are untyped; nothing enforces backend DTO shape. `BACKEND_INTEGRATION.md`/`API_ENDPOINTS_SUMMARY.md` (repo root) predate most of these files — treat them as a Phase 2 starting point, not ground truth; verify against BACK source per task.
