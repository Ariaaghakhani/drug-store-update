# services/api/

## Purpose
Centralized API client layer: one file per backend domain, each exporting a factory `(apiCaller) => ({ methodName(config) {...} })` that wraps raw HTTP calls into named functions. `index.js` aggregates every domain factory into a single `$api` object (registered via `nuxtApp.provide('api', ...)` in [`plugins/api.js`](../../plugins/CLAUDE.md)), so app code calls `$api.<domain>.<method>(config)` instead of hitting `$fetch` directly.

## Key files

The phone-change four back the real `/api/auth/me/phone/*` 4-step flow (`current/send-otp` no body, `current/verify-otp` `{ otpCode }`, `new/send-otp` `{ phone }`, `new/verify-otp` `{ phone, otpCode }`) — verified against `AuthController`/`PhoneChange*Request` DTOs. `changePassword` hits `POST api/auth/me/password` with `{currentPassword, newPassword}` — no OTP, verified against `AuthController.changeMyPassword`/`ChangePasswordRequest`. Both flows return `TokenResponse` (`accessToken`, `message`, `user`) and revoke all other sessions, reissuing the current device's token — caller must re-run `$auth.setToken`/`$auth.setUser`, same shape as login.

## Public surface — the shared request contract
Every domain factory receives a shared `apiCaller` built in [`plugins/api.js`](../../plugins/CLAUDE.md), exposing `get/post/put/patch/delete(url, config)`. Every integration task depends on this contract:
- `config.data` → request body, `config.params` → query string, `config.instance` → which `$fetch` instance to use (`'default'` or `'cms'`; defaults to `'default'`).
- Two `$fetch.create` instances: `default` (baseURL = `runtimeConfig.public.BACKEND_URL`, injects `Authorization: Bearer <cachedToken>` client-side only) and `cms` (baseURL = `runtimeConfig.public.CMS_URL`, adds `Strapi-Response-Format: v4`, server-side only).
- `onResponse` wraps **successful** bodies as `response._data = { data: response._data }` — callers must read `response.data.data` (or `.data.data.content` for paginated lists).
- `onResponseError` instead does `response.data = response._data; delete response._data` — only one level of wrapping. On failure, `error.response.data` holds the raw backend error body directly, `error.response.status` holds the HTTP status. **This asymmetry is easy to get wrong** — a naive `error.response.data.data` is `undefined`.
- `apiCaller.get` memoizes in-flight promises in a module-level `Map` keyed by `url + JSON.stringify(params)` (not including `instance`), auto-evicting on settle. Only `get` de-dupes; `post/put/patch/delete` never cache.
- **No global 401/403 handling** — each caller inspects `error?.response?.status` itself (see [`plugins/auth.client.js`](../../plugins/CLAUDE.md) and `utils/auth.js::logoutAndResetAuthentication`).

## Data flow and dependencies
- Consumed as `$api.<domain>` (`nuxtApp.$api`) or `app.$api.<domain>` (via `useNuxtApp()`).
- **Actual current wiring is thin**: `auth.js` (login/register/OTP, `pages/login.vue`, `plugins/auth.client.js`, `utils/auth.js`; plus the phone-change OTP methods consumed by `components/panel/profile/ChangePhoneModal.vue` and `changePassword` consumed by `components/panel/security/ChangePasswordModal.vue`), `panel/address.js` (`pages/panel/address.vue`, fully wired — list/create/update/delete/set-default all hit real endpoints; also used by `pages/cart.vue`'s checkout modal for address selection), `products.js::fetchProductsList` (`pages/medications/index.vue`), `goods.js` (`getGoods` via `pages/medications/[id].vue`; `createGoods`/`updateGoods`/`filterGoods`/`getTags`/`getProductBatches`/etc. via `pages/panel/products/{index,new,[id]}.vue`'s admin CRUD), `catalog.js` (`listCategories`/`getCategoryChildren` via the same admin product pages; `getCatalogsByType` via `components/panel/orders/CustomerOrders.vue` for order-status label resolution), `orders.js` (`byPerson`/`searchOrders`/`searchOrdersByStatus` via `components/panel/orders/{CustomerOrders,OrdersManagement}.vue` — see [`components/panel/CLAUDE.md`](../../components/panel/CLAUDE.md)), `payments.js` (`checkout`/`quote`, `pages/cart.vue`'s checkout flow), and `analytics.js`'s dashboard section (`getDashboardSummary`, `getLowStock`, `getExpiringGoods` via [`composables/useAdminDashboard.js`](../composables/CLAUDE.md); `getUserActivityChart`, `getCategoryChart` via [`composables/useOwnerDashboard.js`](../composables/CLAUDE.md)) are called anywhere in the app today.
- The remaining domain files (`inventory`, `communication`, `user`, `organization`, `location`, `search`, `medical`, `attachment`, `settings`, `audit`, `dynamic`, `sms`, `blog`), plus `goods.js`'s product-batch functions (path-fixed but not yet consumed by any UI), `catalog.js`'s brand/unit lookups and category-scope CRUD, `orders.js`'s other methods (`listOrders`, `getOrder`, `createOrder`, `deleteOrder`, `byUser`, `byStatus`, `byDate`, order-item/invoice/purchase-order CRUD — unverified-but-plausible, not confirmed against BACK source beyond `byPerson`/the search endpoints), and `analytics.js`'s reports/report-management section, are scaffolded per the pre-existing `BACKEND_INTEGRATION.md`/`API_ENDPOINTS_SUMMARY.md` docs for future admin-panel/store work — treat their shapes as provisional/unverified against the live backend until confirmed against BACK source.
- No shared error-normalization helper exists — each caller re-derives status/message ad hoc (e.g. `plugins/auth.client.js` checks `[401,403]`; `login.vue` just toasts a generic error; `utils/auth.js` swallows errors silently).

## Gotchas
- **Double address domains**: `location.js` (`$api.location`, POST-based `api/addresses/*`, unused/unimported) and `panel/address.js` (`$api.address`, the one actually wired up — `GET /api/locations/provinces`, `GET /api/locations/provinces/{id}/cities`, `POST /api/addresses/{person,create,update,delete}`) both model "addresses" with different endpoints/shapes and separate namespaces.
- **Double blog domains**: `blog.js` (`$api.blog.getBlogPosts`, CMS/Strapi GET) vs. `communication.js`'s blog CRUD (`$api.communication`, backend POST) — same subject, different backends, no naming hint which to use.
- **`products.js` vs `goods.js`**: `products.js` is explicitly commented "Legacy alias" wrapping the same `api/goods/list` endpoint `goods.js::listGoods` covers, but don't assume identical response shape.
- **GET caching is barely exercised**: almost every domain implements list/get as `apiCaller.post(...)` even for pure reads, so only `auth.fetchUser`, `attachment.downloadAttachment`, `blog.getBlogPosts`, `panel/address.getState`, `panel/address.getCity` actually use the de-duped `get` path.
- **`blog.js::getBlogPosts`** spreads `...config` then unconditionally overwrites `params: { populate: '*' }` — silently discards any `params` the caller passed in.
- **Inconsistent leading slash**: most domain files use bare paths (`'api/goods/list'`); `blog.js`/`panel/address.js` use leading-slash paths. Harmless with `$fetch` baseURL joining, but inconsistent style.
- **`auth.js::submitOtp` bug**: calls `this.login(config)`/`this.register(config)` without `return`/`await` — the result is dropped; callers awaiting `submitOtp` get `undefined`. Fix this when touching the OTP flow. (Not touched by the phone-change or password-change work — those are separate, newly-added functions, not fixes to `submitOtp` itself.)
- **`panel/address.js` is now fully wired**: `getState`/`getCity` are real `GET` calls against `LocationController` (`/api/locations/provinces`, `/api/locations/provinces/{provinceId}/cities`), and `addAddress`/`updateAddress`/`deleteAddress` all hit `AddressController` (`POST /api/addresses/{create,update,delete}`). The old `response?.data?.id` bug in the create success handler (in `pages/panel/address.vue`) is fixed to `response?.data?.data?.id` per the envelope rule above.
- **Phone-change flow is NOT under `/api/otp/*`**: `auth.js`'s `sendCurrentPhoneOtp`/`verifyCurrentPhoneOtp`/`sendNewPhoneOtp`/`verifyNewPhoneOtp` hit `/api/auth/me/phone/*`, a separate mechanism from the generic `OtpController` (`/api/otp/send`, `/api/otp/verify`) — the generic one explicitly rejects phone-change codes and vice versa. On success, `verifyNewPhoneOtp` returns a fresh `TokenResponse` because other sessions get revoked server-side; the caller must re-sync `$auth`/`userStore` with the new token, same pattern as login.
- **`goods.js::getGoods` response has no stock field for simple products** — `GoodsDTO` (BACK `product/dto/GoodsDTO.java`) carries no stock/quantity field at all; stock only exists on `GoodsVariantDTO.availableQuantity`, which applies only to variant products. `pages/medications/[id].vue` deliberately omits any stock UI for simple products rather than guessing. Tracked in `FRONTEND_API_TODO.md`.
- **`security/{ActiveSessionsCard,AuthMethodsCard,DangerZoneCard,LoginHistoryCard,SecurityAlertsCard,TwoFAModal}.vue` stay mocked**: BACK has no endpoints for session list/revoke, 2FA, login history, or security-alert prefs (verified repo-wide search of BACK source, Phase 2+8). See `FRONTEND_API_TODO.md` for the 4 proposed-contract entries; only `ChangePasswordModal.vue` in that folder is wired to a real endpoint.
- **Checkout is one call, not create-order-then-pay**: `payments.js::checkout` creates the order, reserves inventory, and creates the payment transaction server-side in a single `POST api/checkout` — never call `orders.js::createOrder` first for a customer checkout flow (that's a separate generic admin endpoint). The bank callback (`GET api/payment/callback/{gateway}`) is server-handled and redirects to `pages/checkout/result.vue`; there is no client-side verify/poll endpoint.
- **Fixed in Phase 3 (goods.js tags/batches, catalog.js categories)**: `getTags` now `GET api/tags` (was wrongly `POST api/tags/list`); `createTag` now `POST api/tags` root (was `.../create`); `updateTag`/`deleteTag` paths were already correct, `updateTag` body must be the nested `{ id, tagDTO }` shape (not flat). `getProductBatches` now `GET api/product-batches` (was `.../list`); `createProductBatch` now `POST api/product-batches` root with body `{ dto }`; `updateProductBatch` now `PUT api/product-batches` (was `POST .../update`) with body `{ id, dto }`; `deleteProductBatch` unchanged. `catalog.js::listCategories` now `GET api/categories?scope=` (was `POST .../list`); `createCategory` now `POST api/categories` root (was `.../create`); `getCategory`/`updateCategory`/`deleteCategory` paths were already correct (`updateCategory` sends a raw `CategoryDTO`, not wrapped). `listCategoryScopes` now `GET api/category-scopes` (was `.../list`); `getCategoryScope`/`createCategoryScope` paths were already correct. `updateCategoryScope`/`deleteCategoryScope` have **no corresponding backend endpoint** (`CategoryScopeController` only exposes list/get/create) — left unchanged, not callable; see `FRONTEND_API_TODO.md`.
- **`catalog.js`'s brand/unit lookup functions (`listCatalogs`/`getCatalog`/`createCatalog`/`updateCatalog`/`deleteCatalog`) were NOT verified in Phase 3** — `CatalogController`'s real base path is `/api/catalogs` (plural), but these still use `api/catalog/*` (singular); out of scope for the products-admin task but needed before a brand picker can work — see `FRONTEND_API_TODO.md`.
- **Order status resolution differs by page**: `CustomerOrders.vue` resolves the catalog-driven payment/order status via `catalog.js::getCatalogsByType({type:'ORDER_STATUS'})` and maps `OrderDTO.statusId` to a label; `OrdersManagement.vue` instead reads the already-resolved `status`/`statusCode` straight off `OrderSearchController`'s indexed `OrderDocument` — no catalog call needed there. Neither page can show `fulfillmentStatus` in the admin list without an N+1 `/api/orders/get` per row — not implemented, see `FRONTEND_API_TODO.md`.
- **CRUD asymmetry across domains**: some have full CRUD (goods, orders, inventory, catalog, user, medical); others are read/update-only with no delete (`settings.js`, `search.js`). Naming also diverges (`getUser`/`listUsers` hit `api/persons/*`).
- **No shared validation/typing** — `config` objects are untyped; nothing enforces backend DTO shape. `BACKEND_INTEGRATION.md`/`API_ENDPOINTS_SUMMARY.md` (repo root) predate most of these files — treat them as a Phase 2 starting point, not ground truth; verify against BACK source per task.
