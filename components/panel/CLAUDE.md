# components/panel/

## Purpose
Presentational building blocks for the pharmacist/admin panel ([`pages/panel/*`](../../pages/panel/CLAUDE.md)): cards, tables, filter bars, and multi-step modals for addresses, orders, products, users, profile, and security settings. Almost all components here are "dumb" (props in, events out) — pages own data, loading state, and persistence.

## Key files
**root** — `DeleteConfirmDialog.vue`: generic confirm-delete modal, reused by users/products pages.

**address/** — `AddressCard.vue` (single address row, edit/delete/set-default), `AddressFormModal.vue` (add/edit modal, own form state + province/city cascading select), `AddressListCard.vue` (wraps `AddressCard` list with skeleton/empty/add-CTA).

**orders/** — `CustomerOrders.vue` (customer's own orders, real data via `$api.orders.byPerson`; each row's "مشاهده جزئیات" links to `/panel/orders/[id]`), `OrdersManagement.vue` (admin order list with stats strip/status tabs, real data via `$api.orders.searchOrders`/`searchOrdersByStatus`/`getStats`; the "بررسی" row action is now a `UDropdownMenu` of fulfillment actions, state-filtered by the order's `fulfillmentStatus` — see Gotchas).

**products/** — `AddProductModal.vue` (create-product form, unused by `pages/panel/products/new.vue` which has its own inline form), `ProductImagesField.vue` (image picker — **contract changed 2026-10-27**: `modelValue` items are now `{file: File, previewUrl}` for a pending local pick or `{id, url}` for an already-uploaded attachment, not plain data-URL strings; the parent page owns the real `uploadMultiple`/`deleteAttachment` calls, this component stays presentational), `ProductMetrics.vue` (KPI strip), `ProductsFilters.vue` (search + category `v-model`, now driven by real `filterGoods`/`listCategories` data), `ProductsTable.vue` (table with skeleton/empty states, near-expiry badges, `canUpdate`/`canDelete`-gated row actions; "موجودی" column renders `موجود`/`ناموجود`/a neutral "نامشخص" badge off the real `product.inStock` boolean since 2026-10-27 — previously always `null`/neutral).

**profile/** — `ChangePhoneModal.vue` (5-step OTP wizard; steps 1-4 now call the real `/api/auth/me/phone/*` endpoints via `$api.auth.{sendCurrentPhoneOtp,verifyCurrentPhoneOtp,sendNewPhoneOtp,verifyNewPhoneOtp}` — step 5 is still a pure success screen with no call), `EmailConfirmationModal.vue` (simulated verification link flow), `PersonalInfoEditModal.vue`, `UserContactDetails.vue`, `UserHeroCard.vue` (emits `avatar-change` with raw `File`), `UserInfoCard.vue`.

**security/** — `ChangePasswordModal.vue` (2-step: current+new password form with strength meter, then success — wired to real `POST api/auth/me/password`; OTP steps were dropped since BACK's `ChangePasswordRequest` only takes `currentPassword`/`newPassword`, no OTP). **Wired for real as of 2026-10-27**: `ActiveSessionsCard.vue` (list/revoke-one/revoke-all via `$api.auth.{listSessions,revokeSession,revokeAllSessions}`), `LoginHistoryCard.vue` (paginated, `$api.auth.getLoginHistory`, gained a `hasMore`/`loadingMore`/`load-more` pagination contract and in-component fa-label maps for `action`/`failureReason`), `SecurityAlertsCard.vue` (`$api.auth.{getSecurityNotifications,updateSecurityNotification}`, the latter **`PUT`** — never `PATCH`, since BACK's CORS only allows GET/POST/PUT/DELETE/OPTIONS — gained a `savingId` prop to disable the switch mid-save with optimistic-rollback-on-error in the parent page). `AuthMethodsCard.vue` had its entire 2FA row removed (no more `twoFAEnabled` prop/`manage-2fa` emit) and `TwoFAModal.vue` was deleted outright — backend confirmed 2FA will never be built (product decision), not a missing-endpoint gap. `DangerZoneCard.vue`'s "حذف حساب" stays a pure toast, no backing endpoint exists or is planned for it.

**users/** — `CreateUserModal.vue` (form: fullName/phone/password/roleId; `password` is required — BACK's real create-staff endpoint needs one — and there's no "حساب فعال" switch at creation, since new accounts are always active), `EditUserModal.vue` (includes `UserPermissionsPanel`, reads `useRolesStore()` directly), `UserPermissionsPanel.vue` (3×4 permission-switch grid: users/products/orders × create/read/update/delete), `UsersFilters.vue`, `UsersTable.vue`.

## Public surface
- Every component uses plain `defineProps`/`defineEmits`; most follow `v-model:x` (`update:open`, `update:searchQuery`, etc.) rather than touching Pinia/composables internally.
- Only exception: `users/EditUserModal.vue` calls `useRolesStore()` directly to relabel `roleFa` on role change — the one panel component that reaches into global state itself.
- **Two exceptions to "components don't call `services/api/*` directly"**: (1) `orders/CustomerOrders.vue` and `orders/OrdersManagement.vue` call `app.$api.orders.*` (now including `getStats` and the fulfillment/COD action functions)/`app.$api.catalog.getCatalogsByType` themselves (via `useNuxtApp()`) rather than receiving data as props — `pages/panel/orders.vue` stays a pure role-switch with no data of its own. (2) `profile/ChangePhoneModal.vue` and `security/ChangePasswordModal.vue` both call `services/api` functions directly (`app.$api.auth.{sendCurrentPhoneOtp,verifyCurrentPhoneOtp,sendNewPhoneOtp,verifyNewPhoneOtp}` / `app.$api.auth.changePassword`) rather than through their parent page — both are self-contained modals that also update app auth state themselves (`app.$auth.setToken`/`setUser`, same pattern as `pages/login.vue::finalizeLogin`) after success, since the backend revokes other sessions and reissues this device's token in both flows. Every other component still follows the prop-in/event-out rule; API calls happen one level up in `pages/panel/*.vue`:
  - `pages/panel/address.vue` → `app.$api.address.{getState,getCity,getAddresses,addAddress,updateAddress,deleteAddress}` ([`services/api/panel/address.js`](../../services/api/CLAUDE.md)) — edit, delete, and set-default now all make real network calls.
  - `pages/panel/products/{index,new,[id]}.vue` → real `services/api/goods.js`/`catalog.js`/`attachment.js` calls (`filterGoods`, `createGoods`, `updateGoods`, `getGoods`, `deleteGoods`, `getTags`, `listCategories`, `getCatalogsByType({type:'BRAND'})`, `uploadMultiple`, `deleteAttachment`) via `useNuxtApp().$api`. No longer reads `useProductsStore()` / `stores/products.js` (now unused, kept as dead code — see [`stores/CLAUDE.md`](../../stores/CLAUDE.md)). **As of 2026-10-27**: the brand field is a real `USelectMenu` bound to `brandId` (not the old free-text `brandTitle` input), and `ProductImagesField.vue`'s picks are uploaded via `attachment.uploadMultiple` (multipart, after `createGoods`/alongside `updateGoods`) instead of being silently dropped — see [`services/api/CLAUDE.md`](../../services/api/CLAUDE.md).
  - `pages/panel/users.vue` → `useRolesStore()` ([`stores/roles.ts`](../../stores/CLAUDE.md)) for permission/filter logic, plus a real fetched list; its list+create flow is now a third exception to the prop-in/event-out rule — the page itself (not any child component) calls `app.$api.user.{listRoles,listStaff,createStaff}` directly, same pattern as `ChangePhoneModal.vue`/`ChangePasswordModal.vue`. Edit/deactivate/delete (`EditUserModal`/`UsersTable`'s row actions/`DeleteConfirmDialog`) still only mutate the fetched list locally, with no real call behind them (see [`pages/panel/CLAUDE.md`](../../pages/panel/CLAUDE.md) for the full contract and the real/mock role-id mismatch it introduces).
  - `pages/panel/security.vue` → **real as of 2026-10-27** for sessions/login-history/security-notifications (`app.$api.auth.{listSessions,revokeSession,revokeAllSessions,getLoginHistory,getSecurityNotifications,updateSecurityNotification}`), plus `ChangePasswordModal.vue` (see exception above). Revoking the current session (or revoke-all) calls `utils/auth.js::logoutAndResetAuthentication(app, {callLogout:false})` then redirects to `/login`, since BACK already invalidated the token server-side.

## Data flow and dependencies
- [`composables/useUserPanelTabs.ts`](../../composables/CLAUDE.md) drives role-based nav/permission gating (`getUserRole`, `hasAccessToRoute`), read by `pages/panel/users.vue` and `products/index.vue` to compute `canCreate/canUpdate/canDelete`, passed down as props to `UsersTable`/`ProductsTable`/`UserPermissionsPanel`.
- [`stores/roles.ts`](../../stores/CLAUDE.md) holds the role→permission matrix consumed by `users.vue`, `products/index.vue`, `EditUserModal.vue`.
- `stores/products.js` (mock) is now unused dead code — `products/{index,new,[id]}.vue` get list/filter/CRUD data from `$api.goods`/`$api.catalog` instead; `stores/user.js` still supplies `currentUser` for address/profile pages.
- Page↔component mapping: `pages/panel/address.vue`↔`address/*`, `products/{index,new,[id]}.vue`↔`products/*`, `users.vue`↔`users/*`, `profile.vue`↔`profile/*`, `security.vue`↔`security/*`, `orders.vue`↔`orders/*`.

## Gotchas
- **Security is now almost entirely real (2026-10-27)**: `ChangePasswordModal.vue`, `ActiveSessionsCard.vue`, `LoginHistoryCard.vue`, `SecurityAlertsCard.vue` all persist to BACK; only `DangerZoneCard.vue`'s delete-account button has no backing endpoint (not a tracked gap — no proposed contract exists). `TwoFAModal.vue` is gone. `orders/*` is real too (see below).
- **Dual order-status display**: BACK models an order's payment/order status as a per-tenant `Catalog` row (`OrderDTO.statusId`, no fixed enum) and a separate orthogonal `fulfillmentStatus` enum (`SHIPPED`/`READY_FOR_PICKUP`/`DELIVERED`/`null`="در حال آماده‌سازی"). Both components show both axes where the data is available:
  - `CustomerOrders.vue` (`$api.orders.byPerson` → paginated `PageResponse<OrderDTO>`, read from `response.data.data.content`) labels the order status by `OrderDTO.statusCode` through `utils/orderStatus.js` (the old `catalog.getCatalogsByType('ORDER_STATUS')` lookup was dropped 2026-10-29; the filter is by `statusCode`). Legacy note: it used to resolve `statusId` via `$api.catalog.getCatalogsByType({data:{type:'ORDER_STATUS'}})` (`CatalogController`'s `/api/catalogs/by-type`, verified against BACK source — order-status rows are seeded with `type=ORDER_STATUS`, `code` ∈ `PENDING`/`PAID`/`FAILED`) and shows `fulfillmentStatus` as a second badge, since `OrderDTO` carries both fields.
  - `OrdersManagement.vue` (`$api.orders.searchOrders`/`searchOrdersByStatus` → `OrderDocument[]`) only shows the payment/order-status badge — `OrderDocument` (the Elasticsearch-backed search index) already has a resolved `status`/`statusCode` so no catalog lookup is needed there, but it has **no `fulfillmentStatus` field at all**, so that axis can't be shown in the admin list without an N+1 `getOrder` call per row (not done). See `FRONTEND_API_TODO.md` for the proposed fix (index `fulfillmentStatus` on `OrderDocument`).
- **Order stats are now a real aggregate (2026-10-27)**: `OrdersManagement.vue`'s stats strip calls `$api.orders.getStats()` once for `{totalOrders,countByStatus,revenueTotal,revenueToday}` — the old "one `size:1` search per status" workaround and the page-scoped "جمع این صفحه" label are gone, replaced by a real "جمع درآمد" tile off `revenueTotal`.
- **No generic update endpoint, by design**: BACK confirmed (2026-10-27) it will never add a generic `/update` route for orders, order-items, or invoices — order status only changes through the dedicated fulfillment/COD actions. The "بررسی" button in `OrdersManagement.vue` is now a `UDropdownMenu` wired to those actions (`shipOrder`/`readyForPickup`/`deliverOrder`/`deliveryFailed`/`returnedToStore`/`notCollected`/`lostOrder`/`damagedOrder`), filtered per-row by the order's current `fulfillmentStatus`; `ship`/`delivery-failed` open a small inline `UModal` for the optional tracking code / required failure reason. A 409 `order.fulfillment.transition` error (invalid transition, e.g. deliver before ship) surfaces via the existing `error?.response?.data?.message` toast pattern.
- **`address/AddressFormModal.vue` now captures a real `cityId`**: province/city `USelectMenu`s select the actual `ProvinceDTO`/`CityDTO` (`id`, `nameFa`, `nameEn`), not just a display name; the emitted `save` payload includes `cityId` and `recipientPhoneNumber` (renamed from the old ad hoc `phone` key). `AddressCard.vue`/`AddressListCard.vue` gained a `settingDefault`/`settingDefaultId` loading prop, mirroring the existing `deleting`/`deletingId` pattern, for the set-default network call.
- **Permission gating is prop-driven, not enforced in the component**: `ProductsTable`/`UsersTable` just hide/disable actions based on booleans passed in; real role→permission resolution lives in the parent pages. A component alone enforces nothing server-side.
- **Modal pattern**: all modals use Nuxt UI `UModal` with `v-model:open`, `dir="rtl"` + `font-dana` wrapper; destructive/cancel-mid-flow modals (`ChangePhoneModal`, `ChangePasswordModal`) have a secondary "cancel confirm" sub-state layered via nested `<Transition>` — closing via the X button doesn't always close immediately.
- **OTP step wizards** manage per-digit input refs manually (no shared composable yet). `ChangePhoneModal` (profile) is real, with one `loadingStepN` ref per step plus `resendingOld`/`resendingNew` for its resend buttons, reading errors via `error?.response?.data?.message` into `useAppToast().error(...)` — follow that same per-step loading/error shape if adding new OTP flows. `ChangePasswordModal` (security) dropped its OTP step entirely once wired for real, since BACK's `/api/auth/me/password` doesn't require one — don't assume every real-wiring task keeps the original step count.
- Tables use native `<table>` + Nuxt UI `UDropdownMenu` for row actions, not a shared data-table component; pagination state lives in the parent page, not in `ProductsTable`/`UsersTable`.
- **Products admin is now server-paginated** (`page`/`size`/`totalPages`/`totalElements` from `GoodsController./filter`'s `PageResponse`, 1-based page), not client-side sliced like the old mock — `ProductsTable`/`ProductsFilters` themselves are unchanged (still dumb props-in/events-out), only `pages/panel/products/index.vue`'s data layer changed.
- **`AddProductModal.vue` is not wired to `products/new.vue`** — that page has its own inline form (goodCode/nameFa/nameEn/brand/categoryIds/tagIds/price/expiryDate/images/isPrescriptionRequired fields posted straight to `createGoods`). Check before reusing `AddProductModal.vue` elsewhere; it still targets the old mock store shape.
