# pages/ (storefront)

Covers everything under `pages/` except `pages/panel/**` — see [`pages/panel/CLAUDE.md`](panel/CLAUDE.md) for that.

## Purpose
Customer-facing storefront routes: marketing/info, browsing/buying medications, cart, authentication, and a basic account dashboard. All use the `default` layout, RTL/Farsi content, target end customers.

## Data flow and dependencies
- `medications/index.vue`: `useAsyncData(..., { server: false, watch })` (client-only on purpose: BACK resolves the tenant from the request `Origin`/`X-Tenant`, which a server-side fetch doesn't carry, same reason `useStoreProfile` loads client-side only). Search → `$api.search.searchGoods` (grouped, one card per model), facets → `searchGoodsFacets` (a separate `useAsyncData` keyed on the request without page/sort, so paging doesn't refetch them; a facet failure just hides the groups). Cards go through `toProductCard`; add-to-cart through `useAddToCart` (a card with several variants opens the product page instead).
- `login.vue`: no fetch on load; all calls on user action against `services/api/auth.js` (`checkUser`, `login`, `loginOtp`, `register`, `sendRegisterOtp`, `forgotPassword`, `forgotPasswordOtp`). On success calls `app.$auth.setToken()`/`setUser()` (from [`plugins/auth.client.js`](../plugins/CLAUDE.md), syncs `stores/user.js`) then `await navigateTo(route.query.redirect || '/panel/dashboard')` — fixed 2026-10-09, was `|| '/'` (sent every login with no explicit `?redirect=` to the storefront homepage instead of the panel) and the `navigateTo` call wasn't `await`ed. `definePageMeta({ layout: 'auth' })`.
- `cart.vue`: reads/mutates the Pinia `cart` store (persists to `localStorage`) for the item list; `handleCheckout()` still redirects to `/login?redirect=/cart` if logged out. Logged-in: `proceedToCheckout()` opens the checkout modal, loads the customer's addresses (`$api.address.getAddresses`, defaulting to the `isDefault` one) and a price `quote` (`$api.payments.quote`) in parallel, and re-quotes on delivery-method/pay-on-delivery changes. Cart items are mapped to `CheckoutItemDTO` as `{ goodsId: item.id, batchId: item.batchId ?? null, quantity: item.quantity }` — `batchId` is always `null` today since the demo `products` store has no batch concept. On confirm, `confirmCheckout()` calls `$api.payments.checkout`; if the response has `paymentUrl` the cart is cleared and the browser goes to `/checkout/redirect?url=<paymentUrl>&gateway=<gateway>&amount=<quote.total>` (internal, **as of 2026-10-28** — previously jumped straight to the external `paymentUrl`; see `checkout/redirect.vue` above), which itself does the external redirect after a short delay; if `cashOnDelivery: true` instead, the cart is cleared and the modal shows an inline success state instead of redirecting.
- `medications/[id].vue`: client-only fetch via `onMounted()` (same pattern as `medications/index.vue`, not `useFetch`/`useAsyncData` — no SSR data) calling `app.$api.goods.getGoods({ data: { id: Number(route.params.id) } })` (the body must go under `data`; a bare `{ id }` sends no body and BACK answers 400) → `services/api/goods.js` → `POST api/goods/get`, unwraps `response.data.data`. Any thrown/missing-data response flips a single `notFound` state (covers both 404 and generic errors) rendering the not-found empty state; no separate toast on failure. `handleAddToCart` → `useCartStore().addItem(...)`, same success-toast pattern as `medications/index.vue`. Images come from `GoodsDTO.attachments[].url` (primary attachment preferred, first as fallback) — there is no flat `images` array on the DTO. **As of 2026-10-27**: renders wishlist (heart) and "notify me" buttons (store-profile flags `wishlistEnabled`/`stockAlertsEnabled`; guests go to `/login?redirect=…`), and a `موجود`/`ناموجود` badge off the real `product.inStock` boolean (backend added `inStock`/`availableQuantity` to `GoodsDTO`) and disables/relabels the add-to-cart button when `inStock === false` — previously this page omitted stock UI entirely since no such field existed.
- `account.vue`, `about.vue`: no fetch, no store access — static/mock or unimplemented.
- Auth/middleware: only `login.vue` sets page meta (`layout: 'auth'`). None of the other storefront pages apply `middleware/auth.js` — `account.vue` renders with mock data even logged out; `cart.vue` enforces login manually in its own click handler.

## Gotchas
- `medications/[id].vue` is now implemented via `services/api/goods.js::getGoods` (`POST api/goods/get`), not `products.js`. `GoodsDTO` gained `availableQuantity`/`inStock` (2026-10-27, backend answer to `FRONTEND_API_TODO.md`) — `availableQuantity` is the sum of variants for a model product (`isModel:true`), `inStock = availableQuantity > 0`; the page now shows real stock UI instead of omitting it.
- `medications/[id].vue` still fetches in `onMounted()`; the home, listing, brand and near-expiry pages use `useAsyncData` with `server: false` — all of them client-only, so no SSR data and weak SEO despite being a Nuxt app. Moving to SSR needs the tenant sent on server-side fetches first.
- **Categories are built but dark for guests**: `GET /api/categories/tree` answers 401 until BACK adds it to `PublicEndpoints` (request in `BACKEND_REQUESTS.md`). `useStoreCategories` treats 401/403 as "unavailable", so the home row and the `/medications` category filter simply don't render; they turn on by themselves once BACK opens the endpoint. The old fake `?category=<slug>` chips are gone — the link is now `?categoryId=<id>`. `StoreLocationCard` (home map) is not on `/` either — `store-profile.location` is deliberately unused, see `utils/storeLocation.js`.
- `cart.vue`'s `AuthModal` is rendered and wired to `@authenticated` but `handleCheckout` never opens it — redirects to `/login` instead, so `AuthModal` here is still dead code on this page (unchanged by the api-9 checkout work).
- `cart.vue`'s checkout modal has no `/panel`-style form validation beyond disabling the confirm button; a failed `checkout` call just toasts `error.response.data.message` and leaves the modal open for retry.
- The checkout gateway selector only lists `MOCK`/`ZARINPAL` client-side — it doesn't check which gateways the tenant actually has configured (no endpoint exists on the storefront side for that yet).
- `account.vue` has no auth guard and no real backend wiring — treat as a UI mock, not a functional feature.
- `login.vue`'s OTP/session state is page-local (refs + `setInterval`, cleared in `onBeforeUnmount`) — no persistence across navigation.
- Listing search and facets are `POST`s, so `plugins/api.js`'s GET de-dup cache doesn't apply — every filter/page change hits the network.
- `middleware/auth.js` no-ops in dev and only checks `localStorage` client-side; no storefront page actually applies it — auth protection here is ad-hoc (`cart.vue`'s inline check) rather than middleware-driven.
