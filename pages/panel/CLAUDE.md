# pages/panel/

Covers `pages/panel.vue` (the panel shell route) and everything under `pages/panel/`. See [`pages/CLAUDE.md`](../CLAUDE.md) for the storefront pages.

## Purpose
`pages/panel.vue` is the shell/layout route for the pharmacist/admin/customer panel: sidebar (desktop) / bottom-nav + slide-up menu (mobile), profile banner, logout, dark-mode toggle, hosting `<NuxtPage />` for all child routes. Auth-gated and role-gated: depending on role (`customer`, `admin`, `owner`), different nav items and page content show. The one app area serving three audiences (self-service customer account pages, admin/owner-only management for users/products/orders) from the same route tree.

## Key files
- `/panel` — `pages/panel.vue` — shell layout: sidebar/bottom-nav, profile banner, logout, color-mode toggle, role-based menu via `useUserPanelTabs`; redirects bare `/panel` to `/panel/dashboard`.
- `/panel/dashboard` — `dashboard.vue` — picks `AdminDashboard`/`OwnerDashboard`/`CustomerDashboard` by role.
- `/panel/orders` — `orders.vue` — `CustomerOrders` for role `customer`, else `OrdersManagement`.
- `/panel/products` — `products/index.vue` — product list/table with metrics, filters, pagination; permission-gated create/edit/delete.
- `/panel/products/new` — `products/new.vue` — create-product form; guarded by `products.create` permission.
- `/panel/products/[id]` — `products/[id].vue` — edit-product form; guarded by `products.update` permission.
- `/panel/address` — `address.vue` — customer address book, fully wired to real API calls (list/create/update/delete/set-default).
- `/panel/profile` — `profile.vue` — personal info now wired to the real `POST /api/persons/update` (via `app.$api.user.updateUser`); contact details and avatar remain client-mocked.
- `/panel/security` — `security.vue` — password, sessions, login history, security alerts now all wired to real endpoints (2026-10-27); 2FA was removed entirely (backend will not build it); danger zone's delete-account stays a toast-only stub.
- `/panel/users` — `users.vue` — user management table; **list and create are now wired to real endpoints** (`GET /api/users/staff` / `POST /api/users/create`); edit/deactivate/delete still only mutate local state (not persisted — see Gotchas). Permission-gated by `users.*`.

Unlike every other page in this folder, `orders.vue` passes no data down — both components fetch their own data directly via `$api.orders`/`$api.catalog` (see that module's CLAUDE.md for the dual-status wiring).

- `products/{index,new,[id]}.vue` now also call `app.$api.goods.*`/`app.$api.catalog.*` directly (see below) — no longer only `address.vue` talking to a real backend.
- `profile.vue` → `components/panel/profile/{UserHeroCard,UserInfoCard,UserContactDetails,PersonalInfoEditModal,ChangePhoneModal,EmailConfirmationModal}.vue`.
- `security.vue` → `components/panel/security/{AuthMethodsCard,ActiveSessionsCard,LoginHistoryCard,SecurityAlertsCard,DangerZoneCard,ChangePasswordModal}.vue` (`TwoFAModal.vue` deleted 2026-10-27).
- `users.vue` → `components/panel/users/{UsersFilters,UsersTable,CreateUserModal,EditUserModal}.vue` + `DeleteConfirmDialog.vue`; uses `useRolesStore`, `useUserPanelTabs().getUserRole`, and now also `app.$api.user.{listRoles,createStaff}` for the create-user flow (see below).

## Data flow and dependencies
- Real backend calls on `address.vue`, via `app.$api.address` ([`services/api/panel/address.js`](../../services/api/CLAUDE.md)): `getState()` → `GET /api/locations/provinces`, `getCity(province)` → `GET /api/locations/provinces/{provinceId}/cities`, `getAddresses({data:{personId}})` → `POST /api/addresses/person`, `addAddress(config)` → `POST /api/addresses/create`, `updateAddress(config)` → `POST /api/addresses/update`, `deleteAddress(config)` → `POST /api/addresses/delete`. Edit, delete, and set-default (update with `isDefault:true`) all now persist via real network calls; set-default has its own `settingDefaultId` loading state alongside the existing `deletingId`/`isSaving`.
- `orders.vue` itself makes no calls, but its two child components now do, directly: `CustomerOrders.vue` → `app.$api.orders.byPerson({data:{personId: userStore.currentUser.person.id}})` + `app.$api.catalog.getCatalogsByType({data:{type:'ORDER_STATUS'}})`; `OrdersManagement.vue` → `app.$api.orders.searchOrders`/`searchOrdersByStatus` (list + stats-tile counts) + the same catalog lookup. See [`components/panel/CLAUDE.md`](../../components/panel/CLAUDE.md) for the dual-status-axis details and known gaps.
- Real backend calls on `products/{index,new,[id]}.vue`, via `app.$api.goods`/`app.$api.catalog`/`app.$api.attachment` ([`services/api/CLAUDE.md`](../../services/api/CLAUDE.md)): `index.vue` → `filterGoods` (`POST /api/goods/filter`, 1-based `page`/`size`, response `PageResponse{content,totalElements,totalPages,page,size}`, now including `inStock`/`availableQuantity`) + `listCategories` (`GET /api/categories?scope=PRODUCT`) for the category filter dropdown, `deleteGoods` (`POST /api/goods/delete`) on row delete. `new.vue`/`[id].vue` → `createGoods`/`updateGoods`/`getGoods` (`POST /api/goods/{create,update,get}`) plus `listCategories`/`getTags` (`GET /api/tags`)/`getCatalogsByType({type:'BRAND'})` to populate `categoryIds`/`tagIds`/`brandId` pickers. **As of 2026-10-27**: `brandId` is sent in the create/update payload (real `USelectMenu`, not the old free-text `brandTitle` input); `ProductImagesField.vue`'s picked files are uploaded via `attachment.uploadMultiple` (multipart, `referenceType:'Goods'`, after `createGoods`/alongside `updateGoods`), and `[id].vue` also diffs/deletes any attachment removed from the picker via `attachment.deleteAttachment`.
- `dashboard.vue` has **no `useFetch`/`useAsyncData`/`$api` calls of its own** — it's a pure role-switch delegating to the dashboard components, which do fetch for real (see [`components/CLAUDE.md`](../../components/CLAUDE.md)). `security.vue` is now real as of 2026-10-27 (see above). `stores/products.js` is now unused dead code.
- `profile.vue`'s personal-info save now calls `app.$api.user.updateUser({data:{id, dto}})` → `POST api/persons/update` (`services/api/user.js`, verified against BACK's `PersonController`/`PersonService`). `dto` is a full `PersonDTO` replace, not a patch (`PersonServiceImpl.update` always sets every mapped field) — `firstName`/`lastName`/`nationalCode`/`birthDate`/`gender` are sent, `phone` is deliberately omitted since BACK treats a missing phone as "no change" for customer-only callers (phone changes must go through `ChangePhoneModal.vue`'s OTP flow; sending a different phone value here throws `ForbiddenException`). Response `PersonDTO` is pushed into both `form` and `userStore.setUser({...currentUser, person: updatedPerson})` so the hero card/initials stay in sync.
- `users.vue` (2026-10-10): on mount it loads real tenant roles via `app.$api.user.listRoles()` (`GET api/roles`) into a page-local `realRoles` ref — a separate list from the mock `rolesStore` used for permission/filter logic elsewhere on this page — then loads the real staff list via `app.$api.user.listStaff()` (`GET api/users/staff`, verified against BACK's `UserManagementController` — "کارکنان", i.e. every user with a role other than customer; **customer accounts never appear in this list**, by BACK design, not a frontend bug) into `allUsers`, the same ref `filteredUsers`/`paginatedUsers`/the table read. Each returned `ManagedUserDTO` is mapped (`mapStaffUser`) to the row shape the rest of the page expects: `roleId` is coarsened to the mock model's `'owner'`/`'admin'` via `mapStaffRoleId` (`ROLE_STORE_ADMIN`→`'owner'`, anything else→`'admin'`, same heuristic as `composables/useUserPanelTabs.ts::getUserRole`), `roleFa` prefers a matching real `RoleDTO.description`/`name` over the mock `rolesStore` label, `lastLoginFa` is `lastLoginAt` formatted via `toLocaleDateString('fa-IR')` or `'هرگز'` if the user never logged in, and `permissions` still comes from the mock `getRolePermissions(roleId)` (see the role-id-mismatch gotcha below). Submitting `CreateUserModal` calls `app.$api.user.createStaff({data:{firstName, lastName, phone, password, roleIds:[form.roleId]}})` → `POST api/users/create`, splitting the modal's single "نام و نام خانوادگی" field into `firstName`/`lastName` on the first space; on success it re-runs the same `listStaff` fetch (`fetchUsers()`) rather than hand-building a row, matching `address.vue`'s refetch-after-mutate pattern. `CreateUserModal.vue` gained a required `password` field (BACK's `NewAccountRequest.password`, validated server-side against the tenant's password policy — no client-side strength check) and dropped its "حساب فعال" switch, since `createStaff` has no at-creation active/inactive flag (new accounts are always active).
- Role resolution: `useUserPanelTabs().getUserRole()` reads `userStore.currentUser?.roles` (BACK's real role-name array from `UserDTO`/`TokenResponse.user` — `ROLE_STORE_ADMIN`→`'owner'`, `ROLE_CUSTOMER`→`'customer'`, any other role name→`'admin'`), falling back to a legacy singular `currentUser?.role` string (validated against `['customer','admin','owner']`) only if `roles` is absent, and to `'admin'` if neither is recognized. Fixed 2026-10-09 — previously only read the singular `role` field, which the real login response never sets, so the panel menu/route-access never actually varied by role for a real logged-in user (every session fell through to the `'admin'` default). See [`composables/CLAUDE.md`](../../composables/CLAUDE.md).
- `users.vue`/`products/*` branch on fine-grained CRUD permissions from `useRolesStore().roles` (5 roles: owner/admin/pharmacist/support/customer) matched against `getUserRole()`'s 3-role output — a model mismatch, see Gotchas.
- Middleware: [`middleware/panel-access.js`](../../middleware/CLAUDE.md) exists but is **not referenced by name** anywhere; `pages/panel.vue` instead defines its own inline middleware duplicating the same logic.

## Gotchas
- **Dev bypass everywhere**: every guard (`pages/panel.vue`'s inline middleware, `panel-access.js`, `auth.js`) short-circuits with `if (import.meta.dev) return` — in local dev, all auth/role checks are skipped and the panel is reachable unauthenticated.
- **Role model mismatch**: `useUserPanelTabs` only knows 3 roles (`customer`/`admin`/`owner`) for menu/route access, but `stores/roles.ts` defines 5 (adds `pharmacist`, `support`) with distinct permission sets used by `users.vue`/`products/*`. A `pharmacist`/`support` user falls through to `'admin'` for menu purposes while still getting pharmacist/support-level permission checks elsewhere.
- **Most "management" pages aren't wired to a backend**: `security.vue` is pure client-side mock state; `profile.vue`'s contact-details/avatar sections still are too; `users.vue` is now mixed — list and create are real, but **edit/deactivate/delete only mutate the local `allUsers` ref** (`onSaveUser`/`onDeactivate`/`confirmDelete`), with no corresponding call to BACK's real `PUT /api/user-roles`, `POST /api/users/{deactivate,activate,lock,unlock}` (no real `/delete` exists for a staff account at all — BACK only supports deactivate/lock, never a hard delete). Any of those three actions is reverted by the next `fetchUsers()` call (e.g. after creating another user) or page reload. `address.vue`, `orders.vue`'s children, `products/*`, `profile.vue`'s personal-info save, and `users.vue`'s list+create talk to real endpoints: `address.vue` is fully wired (create/edit/delete/set-default all persist across reload); `orders.vue`'s children have no update endpoint at all for orders (see `FRONTEND_API_TODO.md`).
- **`users.vue` only ever lists staff, never customers**: `GET api/users/staff` is explicitly "کاربرانی که نقشی غیر از مشتری دارند" (BACK's `UserManagementServiceImpl.listStaff`, filtered on `TenantRoles.CUSTOMER`) — there is intentionally no customer row in this table anymore (the old mock data had 3). `roleFilterItems`/`statusFilterItems` still offer "مشتری"/every mock role as filter options regardless (sourced from `rolesStore`, unchanged) — picking "مشتری" will just always show an empty table, not an error.
- **Real role data and the mock role data use incompatible id spaces, bridged only one-way**: `realRoles`/`realRoleSelectItems` (real, numeric `RoleDTO.id`) feed `CreateUserModal`'s picker and `createStaff`'s `roleIds` payload; `roleSelectItems`/`roleFilterItems`/`getRolePermissions`/`canCreate`/`canUpdate`/`canDelete` all still key off `rolesStore`'s mock string ids (`owner`/`admin`/`pharmacist`/`support`/`customer`). `fetchUsers`'s `mapStaffUser` bridges this *for display* by coarsening every fetched user's real role name(s) down to just `'owner'` (`ROLE_STORE_ADMIN`) or `'admin'` (anything else, including any custom staff role a tenant created) — so a real `pharmacist`-equivalent custom role still can't get distinct pharmacist-tier permissions/badge color here, it's indistinguishable from plain `'admin'`. `EditUserModal`'s role picker still only offers the 5 mock roles and, per the bullet above, doesn't persist a reassignment to BACK at all.
- **`profile.vue`'s birthDate field sends a Gregorian ISO date through a Jalali-styled free-text input** — no calendar-conversion library exists in the project yet, so a real Jalali date typed by the user is stored as a nonsensical Gregorian date rather than converted. See `FRONTEND_API_TODO.md`.
- `products/new.vue`/`products/[id].vue` call `await navigateTo(...)` synchronously at `<script setup>` top level if the permission is false **at setup time** — a permission that becomes true later (async role load) won't retroactively show the form.
- `products/[id].vue`'s "not found" state is now driven by `loading`/`product` refs from `getGoods` (shows "محصول یافت نشد" once the fetch settles with no product), not a `String(id)` comparison against a mock store.
- **`GoodsDTO` gained a real stock field and a real image-upload path (2026-10-27)**: `ProductsTable`'s "موجودی" column now shows `موجود`/`ناموجود` off the real `inStock` boolean (neutral "نامشخص" only for a genuinely null/missing value), and `ProductImagesField.vue`'s picks are uploaded via `attachment.uploadMultiple` after/alongside `createGoods`/`updateGoods` rather than silently dropped.
- `goodCode` is required by BACK (`GoodsServiceImpl.save`, 400 if blank) but wasn't in the old mock form — `new.vue`/`[id].vue` now have an explicit "کد کالا" input and both submit buttons are disabled until it's non-empty.
- `users.vue` computes `canCreate/canUpdate/canDelete` once from the *viewer's own role* — no protection against a lower-privileged admin editing a higher-privilege (owner) user via `EditUserModal`.
- `pages/panel.vue` gates its whole panel UI behind `userStore.currentUser || isDev` inside `ClientOnly` — first-paint behavior differs meaningfully between dev and prod.
